1. Technical Explainer: Workflows vs. Agents

In contemporary software marketing, "agent" is frequently applied as an indiscriminate label for any multi-turn conversational AI. However, Anthropic's canonical engineering reference, Building Effective Agents, defines the distinction not by conversational breadth, but by who orchestrates the control flow:

⚡ A Workflow

An orchestrated system where LLMs and tools are coordinated through predetermined, hardcoded code paths and state transitions.

  • Control Flow: Fixed execution tree designed in advance by human developers.
  • Common Patterns: Prompt Chaining, Routing, Parallelization, Orchestrator-Workers, Evaluator-Optimizer.
  • Autonomy: Zero procedural autonomy; model cannot decide to invent steps or bypass gates.
  • Predictability: Highly deterministic, consistent, and easier to debug.

🤖 An Agent

An autonomous system where the LLM dynamically directs its own control flow, tool usage, and stopping conditions in an iterative loop.

  • Control Flow: Emergent runtime trajectory dictated by model reasoning.
  • Common Patterns: ReAct (Reason + Act), Plan-and-Solve, Autonomous Reflection loops.
  • Autonomy: High procedural autonomy; model decides what tools to call and when to finish.
  • Predictability: Flexible in ambiguous environments, but prone to compounding errors.

Classifying the FL-04 Literature Synthesis Pipeline

In our previous assignment (FL-04), we developed the Source-Grounded Study Notes & Literature Synthesis Pipeline for MindGuard AI, which synthesized five clinical NLP papers using Google NotebookLM and a Claude Project.

Under these definitions, FL-04 is unequivocally a Workflow, not an Agent. The system implemented an Orchestrator-Worker Prompt Chain with an Evaluator Gate. Every paper moved through an identical, non-negotiable four-step pipeline (Extract $\rightarrow$ Synthesize $\rightarrow$ Draft $\rightarrow$ Audit). At no point could the model decide to independently search for an additional paper, query an outside database for missing baseline data, or skip Step 2. A human researcher orchestrated the handoffs along a pre-ordained track.

The Model Context Protocol (MCP) & The Three Primitives

The Model Context Protocol (MCP), open-sourced by Anthropic, resolves the $M \times N$ integration problem by providing a universal protocol (the "USB-C port for AI") that connects LLM clients to external data sources and tools over JSON-RPC 2.0. MCP exposes three distinct primitives:

1. Tools (Executable)

Model-callable functions with defined JSON schemas that produce side effects or retrieve dynamic computational results (e.g., read_file, query_database, fetch_api).

2. Resources (Passive Context)

Read-only data endpoints identified by URIs (e.g., file:///logs/triage.log) that provide ambient contextual grounding without computational execution.

3. Prompts (Templates)

Server-defined reusable prompt templates (e.g., /audit-clinical-citations) that clients render directly into UI menus with structured arguments.

Concrete Agent Upgrade for FL-04: Autonomous Clinical Literature Synthesizer

To upgrade FL-04 into an autonomous Agent, we replace the human-driven prompt chain with a continuous ReAct loop equipped with three MCP tools: mcp-arxiv-search, mcp-filesystem, and mcp-clinical-validator.

Given the objective "Synthesize current evidence on transformer suicide risk classification and draft Section 2.3," the agent dynamically queries arXiv via MCP, reads candidate PDFs, and inspects extracted tables. If an extracted paper lacks sample size details, the agent autonomously decides to query the UMD dataset repository to verify the baseline before drafting, looping until its internal verification gate passes.
